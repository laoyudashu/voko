## 结论

**存在首版范围膨胀，主要在双 Web 完整交付、执行规格的多版本调整，以及计划页的多视图和自动状态联动。总体架构方向有依据，不能凭“10 张服务端表＋2 张本地表”就判定过度。**

建议收紧首版产品行为，保留客户云直传、动态成员授权、真实交付确认、固定资产引用和执行恢复。另有两项架构边界需要先明确，但不能直接归类为过度设计。

本文 P1 表示开发前应处理的范围或架构问题；P2 表示适合从首版推迟的功能。

## 一、有证据的首版范围膨胀

### 1. [P1] 同时承诺两套 Web 完整交付

证据：[整体计划第 71 行](/Users/laoyu/Documents/ChatGPT/open_voko/docs/plans/2026-09-07-group-collaboration-development-plan.md:71)要求 Lite Web 和 Chatroom Web 均完成项目 UI。

用户要求 Web 群协作，但未明确要求两个入口首发功能完全对等。云配置、看板操作、权限失效、上传确认和任务操作因此都增加双端实现与验证工作。不能据此推算总工期翻倍，但这确实扩大了首版交付范围。

建议：先选一个完整项目入口，优先考虑 Chatroom Web；Lite 保留执行能力、必要状态和打开项目的入口。打开项目时的登录与授权衔接仍需验证，不能假定已有无缝跳转。

取舍：首版不能在 Lite Web 内完成全部项目管理。该削减是待采纳建议；若用户要求两个入口等价，就应恢复为明确需求。

### 2. [P1] 为启动后修改分工和依赖建立多版本机制

证据：[数据库附件第 65 行](/Users/laoyu/Documents/ChatGPT/open_voko/docs/plans/2026-09-07-group-collaboration-database-design.md:65)规定执行后调整形成新规格及必要的新 attempt；[第 95 行](/Users/laoyu/Documents/ChatGPT/open_voko/docs/plans/2026-09-07-group-collaboration-database-design.md:95)和[第 99 行](/Users/laoyu/Documents/ChatGPT/open_voko/docs/plans/2026-09-07-group-collaboration-database-design.md:99)按执行规格保留依赖与资产关联。

原稿已经禁止覆盖正在执行的规格，不能将其批评为允许任意原地修改。额外复杂度在于：改动是否使下游失效、旧成果是否可复用、新旧规格如何收敛、旧回执怎样影响新的协作状态。这些语义尚未明确，首版却已经为多版本调整设计结构。

建议：启动前可调整；启动后冻结目标、分工、依赖和输入。首版支持一层子任务、并行执行及汇总。需要改变协作目标或依赖时创建新任务；同一规格的明确失败重试继续新增 attempt。

取舍：首版不支持在同一任务中修改执行后的协作结构并自动重算下游。保留执行快照、固定输入版本、重试历史和迟到回执隔离。删除可变规格功能不等于删除用于并发控制的 `row_version`。

### 3. [P2] 计划页同时提供表格视图和自动完成

证据：[整体计划第 58 行](/Users/laoyu/Documents/ChatGPT/open_voko/docs/plans/2026-09-07-group-collaboration-development-plan.md:58)规定依据任务与验收自动完成事项；[第 65 行](/Users/laoyu/Documents/ChatGPT/open_voko/docs/plans/2026-09-07-group-collaboration-development-plan.md:65)同时要求看板和表格。

建议：首版保留独立计划入口、固定列看板、负责人、截止日期和任务关联；关联任务进度只读显示，事项状态由人调整。任务状态始终来自真实执行。

取舍：首版没有表格切换和事项自动关闭。拖动看板仍不能将失败或执行中的任务改成成功。

## 三、不建议削掉的复杂度

| 保留项 | 必要原因 | 首版控制范围 |
| --- | --- | --- |
| 客户私有云、直传直取 | 符合 VOKO 不存储或中转资产正文的要求 | 只接七牛一种经验证的方案 |
| 当前成员校验、授权版本、短期文件授权 | 动态退群、重新入群与旧回执需要正确隔离 | 不做逐文件自定义 ACL；如实说明旧链接的剩余有效期 |
| 任务和 attempt 分开 | 明确重试、重复投递、迟到回执不能混为一次执行 | 保留必要历史，不增加面向用户的 Run 层级 |
| 固定资产版本与下载校验 | 下游必须读到明确的前序成果，不能悄悄变化 | 实测一种防覆盖或稳定引用方案；不同时建设所有备选方案 |
| 本地持久化、去重、未知结果处理 | 超时或重启不能推断未执行，更不能自动再次调用模型 | 优先复用现有组件；不新建通用工作流平台 |
| 状态与事件同事务 | 任务更新后必须能恢复通知 | 现有拟议事件表兼作待通知记录，不另建消息总线 |
| 跨主人、跨设备真实交付验证 | 这是群协作的实际授权和执行场景 | 两种已验证 Provider 即可，不覆盖所有组合 |
| 公告复用与内部规则隔离 | 公开群公告和成员内部指令可见范围不同 | 保留 notice；规则仅可选字段与执行快照 |
| 基本迁移、回退和凭证轮换 | 上线后需保住旧群、历史记录与客户文件 | 复用现有管理和日志能力，不建设独立运维平台 |

固定资产引用并不要求首版提供丰富的版本管理界面。[原计划第 73 行](/Users/laoyu/Documents/ChatGPT/open_voko/docs/plans/2026-09-07-group-collaboration-development-plan.md:73)已经允许不支持预览时仅下载，因此不能将“所有文件必须预览”列为原稿问题。

## 四、关于数据库数量

没有充分证据要求把 10 张服务端表强行压缩到某个数字。项目、连接、计划、任务、执行、资产、版本和关联关系各有明确用途；合并任务和执行，或将依赖塞进缺少约束的 JSON，可能将复杂度转移到应用代码。

更合适的顺序是先减少首版行为，再复核相应字段和约束。可优先审视执行规格多版本及其关联字段；资产逻辑对象和具体版本可继续分开。本地两张表最终是否需要，应以组件复用验证结果决定，而非仅凭命名或表数判断。

## 五、建议的最小交付流程

1. Chatroom Web 提供动态、计划看板、任务、资产和必要设置；Lite 负责执行与基本状态。
2. 管理员配置一个客户私有云空间，实际读写及权限验证通过后启用资产协作。
3. 用户选择负责人和参与 Agent；在各主人允许的范围内确认分工，启动后冻结执行规格。
4. 两个不同主人、不同设备、不同 Provider 的 Agent 并行工作，将成果直传客户云。
5. 汇总任务获取已固定的前序资产版本、下载校验，再生成最终成果。
6. 用户人工验收；任务显示真实结果，计划事项由人调整状态。
7. 验证退群撤权、重复通知、上传中断、Provider 中断、结果未知和恢复；结果未知不得自动重跑。

该流程仍包含真正的多 Agent 分工、并行、产物依赖和汇总。推迟双 Web 完整管理、计划表格、启动后改分工与依赖、事项自动完成，以及通用质量验收和丰富版本操作 UI。
