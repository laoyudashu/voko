# Provider 访客安全开发计划 v2

日期：2026-09-07。状态：**用户已批准实施，P0 代码与定向回归已完成；完整门禁仍有 3 项已确认的基线失败；未部署。**

依据：[评估与本地复现](provider-visitor-security.md)、[独立 Agent 审查及采纳记录](independent-admission-design-review.md)、随后逐 Provider 的指令检查。此文件替代原报告的修复提纲及对话中超出本文件范围的设计设想。

## 1. 目标与收敛

第一阶段只修两个 P0：

1. 新接收消息的准入拒绝，不能通过 Push、Provider Pull、私聊恢复或群历史上下文重新进入 Agent。
2. 群聊显式 @ 与 @所有人都不得绕过目标 Agent 的黑名单和下架限制。

达到目标还必须处理异步审核、群消息共享、未 @ 上下文、分页和提交前复核。这些是现有代码中的实际依赖，不是新产品能力。

本阶段不做：通用 Tool Broker、权限规则 DSL、policy_version/epoch、持久化有效 @、新队列系统、自动重审补发、旧历史逐条导入 UI、全 Provider OS 沙箱、全局禁用 Provider。

## 2. 最小数据与职责

新增一张小型、持久化的消息准入表，候选名 `agent_message_admissions`：

- 复合主键：`agent_id, message_id`。
- 状态：`pending / allowed / denied`。
- 原因码及创建/更新时间；按既有审计展示实际需要关联必要的审核元数据，不复制正文。
- 不保存 policy_version，不保存 canTrigger，不把 native Provider 权限策略复制进来。

使用几个明确的函数完成当前访问检查、群资格/触发计算、Agent 可读取消息查询。最终命名遵循仓库现有模式，不构建通用规则执行器。

必须区分两层：

| 内容决定 | 自动接待条件 |
|---|---|
| 已明确拒绝或尚未审核的原文不可进入 Agent；allowed 仍须通过当前访问检查 | @、MANUAL、计费、是否存在可用通道等决定是否此刻启动任务 |
| 黑名单/审核拒绝等已经作出的拒绝，不因解除黑名单自动重投 | MANUAL、计费暂停不能不加区分地变成永久内容拒绝 |

未发布状态在当前使用时阻止自动接待；其历史消息不凭重新发布自动补发。本阶段不新建补发语义。私聊白名单仅作用于私聊，计费规则不扩展到群聊。

具体拦截原因映射先写成窄的代码契约和用例，逐个确认现有自动接待/上下文行为；不得把 `markIntercepted` 的所有原因直接映射为 denied。

## 3. 开发顺序

### S0：建立边界回归和迁移范围

- 以现有复现脚本转成真正的失败回归；包括 A 拒绝、B 允许的同群共享消息。
- 列出所有进入 Provider 的内容来源：即时消息、离线/skipForward、合并消息、通用 CLI 历史、conversation-context、群 recentMessages、Provider Pull，以及附件和摘要引用。
- 检查普通主人历史 API 与 Provider 可调用历史 API 的授权边界。不可只修改 fetch_new_messages，却留下同一访客执行会话可无条件读取原文的另一条接口。此处仅复用已有调用者/会话身份；如果缺少可强制的身份，列为明确阻断项，不能靠提示语称已隔离。
- 在合成数据中确定 schema 迁移和旧记录分类；生产只读数量统计在实施/迁移授权后进行，不因本轮计划请求直接访问生产。

### S1：小型准入记录与审核入口

- 对可能触发处理的新消息，原文保存与对应 Agent 的 pending 初始化保持原子性，随后启动有界准入检查。多 Agent 收到同一群消息时分别处理，不能把第二个 Agent 当重复消息整体跳过。
- 把审核从“有 dispatcher 才进入”的 forwardToAgent 流程拆出，Push 不可用/Pull-only 也先完成相同检查。
- 复用现有异步审核 Promise，完成才 allowed；拒绝/失败有明确终态，不允许缺记录或 pending 暂时当 allowed。
- 非 @ 群消息收件时仍执行同步黑名单等确定性检查，拒绝按 Agent 立即持久化。惰性处理只针对昂贵审核，不能延迟记录已知拒绝，以免解除黑名单后原文首次审核被放行。
- 非 @ 群消息若没有已完成内容决定，可以暂不建立审核记录；缺记录默认不可注入，不等于 allowed，也不伪装为正在审核。仅在有界历史候选窗口选中时启动审核并写 pending，完成后才可注入；明确的已有拒绝不得重判为允许。避免为全群所有 Agent 对所有闲聊立即跑模型审核，检查失败有终态，不建立后台永久任务队列。
- 停止某个 Agent 的群审核覆盖共享 `messages.content`。复用既有 Agent 范围的审计记录/展示入口，必要展示适配包含在本提交；审核原文、其他 Agent 的读取和审核统计均要回归。
- 保留消息原始内容用于有授权的主人审计。普通 Provider 读取不得返回拒绝原文或含原文的审核 JSON。

### S2：群资格、黑名单、下架与 @

先资格检查，再路由选择。抽取 GroupReplyRouteResolver 已有群成员/管理员逻辑，普通首次消息、精确回复、@所有人、Pull 都使用它；无旧路由不得跳过资格检查。

| 输入 | 处理契约 |
|---|---|
| 正文昵称/引用文字中的 @ | 不触发，结构化 mention.uids 才作为目标 |
| 普通成员合法 @A | A 通过自身黑名单、发布状态、群资格、审核后才能执行 |
| 合法 @A @B | 分别决定，不把一个 Agent 的拒绝传播到另一个 Agent |
| 群主/管理员 @所有人 | 仅在有权接待的目标 Agent 集合中分别检查，不全局放行 |
| 普通成员非法 all=true，包括混有显式 uids | 不触发该请求；保留现有受保护路由对非法 all 的拒绝语义，不新增“忽略 all”的产品行为 |
| 未 @ 的正常群消息 | 不主动启动；符合内容准入和可见范围时可成为后续群上下文 |
| 目标 Agent 拉黑发送者或已下架 | 对该 Agent 不触发；其后续输入也不绕过当前访问限制 |
| 邀请、系统通知、自身回流 | 继续不作为新访客任务触发，不从正文声明推导可信身份 |

- 成员、角色来自可信群信息，all 采用严格布尔校验；去重 UID，畸形结构不猜测扩展目标。
- 复用既有短期成员缓存；接入已有成员变更失效事件，不另建常驻同步服务。
- 查询失败或资格未知时不执行。本次失败必须终结为可见原因，不能无限 pending；自动补发不属于本期。
- 黑名单为 Agent 范围；不在群里公开其私人名单，也不为 @所有人的拒绝逐 Agent 刷屏。

### S3：共同读取规则与局部分页修复

- 当前访问检查 + 持久内容决定 + 用途（触发/上下文）共同决定能否返回内容。
- `fetch_new_messages` 的单频道、阻塞、全量路径一致；保持原来的频道独立 message_seq 和 clientId，不引入全局序号或新拉取协议。
- 过滤发生在可正确分页的位置。游标只跨过本次已返回或确定可跳过的记录；不能跨过真正待触发且正在检查的 pending，或因总 limit 被截掉的可返回记录。
- 触发游标可以跨过不触发的非 @ 消息，包括仅供上下文、尚未启动昂贵审核的消息；它们不能借此进入 Pull 结果。候选历史由独立的有界查询按需审核，不依赖触发游标。因此非 @ 闲聊不阻塞后续合法 @，也不需要新状态或后台全量审核。
- 修正已复现的全量 Pull 先推进各频道 MAX、再截断结果问题，使用独立用例验证；本轮不执行 git 提交。
- pending Promise 必须有界。启动时仅把已确认属于失效旧执行的遗留 pending 终结为 `ADMISSION_CHECK_INTERRUPTED`，保留审计原因；不能误处理仍在另一活动进程执行的记录。按仓库单运行实例/恢复机制实现，不新建分布式租约系统。
- `onlyNew` 显式首次锚定仍是用户选择跳过旧消息的语义，和普通分页分开测试，不借此掩盖漏读。
- 两套私聊恢复与群上下文都改为共同查询；群上下文必须带目标 agentId。

### S4：提交边界与已拼接历史

- 队列保留原始消息/来源 ID；不要提前把群 recentMessages 拼进 rawContent 并永久复用。
- 在现有最后可变更提交点，从获准记录构造本轮上下文。Provider 有内部等待时，提交回调需检查本轮当前消息及所引用历史来源是否仍可用；不能只查最后一条 fromUid。
- 如果等待后发现权限变化，拒绝尚未提交的整轮或在尚可安全重建的位置重建；不通过字符串替换删除敏感片段，不自动重投结果未知的轮次。
- 优先直接读当前黑名单/发布状态，不新增版本递增体系。首次访问校验与最终提交校验是不同时间点的同一规则。
- 不声称可消除已经进入原生 Provider 会话的旧内容；已有会话重置、撤回已提交任务、追踪他人引用来源不属于这两个 P0。

### S5：完整验收后才考虑启用

先运行相关单元/组件和迁移检查，再执行仓库要求的变更门禁。没有新失败或未覆盖风险不机械重复全量测试。

必要回归：

1. 新接收黑名单/硬拒绝消息经 Push、Pull、CLI 历史、群上下文均不可重新暴露。
2. 同群 A 拒绝/B 允许；审核不改写 B 的原文；重复收件独立且幂等。
3. 未 @ 的安全历史保留；被拒未 @ 历史不能夹带进入下一次 @。
4. 首次群消息、旧路由、精确回复均覆盖成员资格；合法/非法 all、显式 UID、畸形 mention、下架等路径一致。
5. pending 期间 Pull 不返回；正常完成可读；失败/中断不永久卡住频道；Pull-only 有审核。
6. 单频道/阻塞/多频道/过滤后空页/总 limit/onlyNew 不漏读；不跨越待触发审核 pending，但非 @ 未审历史不阻塞后续合法 @。
7. 排队后当前消息发送者或群历史发送者被拉黑，不再提交已有拼接原文。
8. MANUAL、计费与上下文不误作永久安全拒绝；既有业务条件不因 Pull 放宽。
9. 原有附件、A2A、Owner、精确会话路径保持独立授权语义；失败不自动跨通道放宽限制。
10. 升级、重复迁移、数据写入失败以及明确拒绝/未知旧历史分类有证据。

## 4. 旧历史：独立迁移决定，不能偷换安全结论

先区分：已知审核/拒绝证据、可确认的正常记录、没有当时准入证据的未知记录。没有记录不等于被拒，也不等于已获准。

| 迁移选择 | 行为与代价 |
|---|---|
| 严格 | 未知旧历史不自动注入，只保留有授权的主人查看；减少部分会话记忆 |
| 兼容 | 对未知旧历史按当前权限与审核重新判定；可保留更多上下文，但不能证明它过去从未被拒绝 |

明确被拒的记录不能仅因当前放行而自动重投。先统计影响数量再由用户确定未知历史选择；不预设全量清空，也不开发逐条授权/导入 UI。未定迁移规则不妨碍完成代码与合成数据测试，但阻止生产启用和“存量全部安全”声明。

## 5. 后续 Provider 工作单独排期

P0 验收完成后再推进以下项目，不并入第一批：

| 顺序 | 工作 | 验收 |
|---|---|---|
| P1-a | WorkBuddy 无工具模式双 --agent 选择冲突；DeepSeek Harness CLI 未映射 Agent preset | 证明指定专家确实加载，同时不以开放不受控工具作为修复手段 |
| P1-b | 逐 transport 验证工具/文件读取范围/网络/审批/MCP/插件边界，纠正能力声明 | 当前 runtime fingerprint 下的可重复无副作用 canary；送达成功与安全有效分开 |
| P1-c | 备用通道必须满足本轮已有权限要求 | 主通道失败不扩大工具权限；Pull 不被标为等价隔离替代 |
| 后续按证据 | 环境变量收窄、原生会话已有数据、受控工具代理 | 先验证实际必要性和认证依赖，另行设计，不泛化重构 |

当前 Catalog 中 OpenHands、Amazon Q、ZCode、豆包办公、Others 仅 Pull；Mock 仅测试，不把未启用适配文件当现有运行通道。

## 6. 本轮实际交付

用户明确“实施”后，S0–S4 已落地，S5 最终检查结果见 [实施验收记录](provider-visitor-implementation.md)。

- schema v10 新增按 Agent/消息区分的准入表；messages.admission_received_at 仅标识新入库来源，旧记录保持 NULL，不代表准入许可。迁移先备份，不重审放行未知旧消息。
- Push、Pull、私聊恢复、群历史及 E2EE v2 直接执行路径共用准入决定；纯 Pull 在运行实例内按需审核有界群历史，短 CLI 不启动后台审核。
- 群首次消息与精确路由复用成员资格检查；结构化显式 @、管理员 @all、黑名单和发布状态按目标 Agent 检查。
- 当前消息、合并批次与引用历史在实际提交前再次检查；各 Provider 内部等待后的提交点保留回调。
- Owner 原文查看仅授予有效 Web session；MCP/CLI 历史与人工介入返回受过滤，消息 WS 和 Console 后续快照也覆盖原文边界。
- 未加入策略版本、通用权限框架、新队列或自动重投。独立最终源码复核未发现尚未关闭的明确阻塞项。
- 没有提交、推送、部署或生产数据库/配置修改。未知旧历史迁移选择仍须在生产启用前单独确定；本轮不声称存量历史或原生 Provider 沙箱全部安全。
