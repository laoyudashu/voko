# 独立 Agent 设计审查与采纳记录

日期：2026-09-07。审查对象：本次对话提出的消息准入统一与群聊 @ 安全修复方案。

独立审查 Agent：`independent_design_review`。审查以现有源码为依据，独立提出反例；未修改功能代码、运行生产服务或调用真实 Provider。本文由主 Agent 根据审查反馈整理，并记录主 Agent 的采纳判断。

## 结论

**存在局部过度设计，须收敛后实施。** 两个 P0 的目标成立；每 Agent 的持久化准入维度和异步审核 pending 有真实必要。策略版本体系、持久化 @ 资格、通用权限引擎、自动审核恢复/补发队列及旧历史导入 UI 都不是本次目标所必需。

独立审查并未建议退回“只加黑名单 if 判断”。它指出原方案还遗漏了共享群消息改写、提前构造的群上下文、Pull-only 审核和分页等实际问题。

## 反馈、证据与决定

| 独立反馈 | 源码依据 | 主 Agent 决定 |
|---|---|---|
| 保留按 Agent、消息区分的准入记录 | `messages.id` 全局主键；群消息由多个 Agent 共用，messenger.ts 群聊 UNIQUE 分支 | 采纳；小表有必要，不用共享消息上的单一 blocked 标志 |
| 不复用路由状态作为准入 | database.ts 的 provider_message_routes 有 expires_at、会话关系及路由生命周期；recordInbound 会更新 active | 采纳；强行复用会把路由有效与内容获准混为一谈 |
| pending 不能删除 | messenger.ts forwardToAgent 的异步模型审核在 Promise 完成后才能决定放行 | 采纳；仅保留 pending/allowed/denied 三态 |
| 审核不能依赖 Push 存在 | forwardToAgent 在没有 dispatcher 时先返回，之后才是异步审核 | 采纳；接收与审核先独立完成，Push/Pull 后选择 |
| 不需要 policy_version | 当前权限在使用时可直接查库；版本机制要求所有修改入口可靠递增 | 采纳；不新增 epoch/digest/revision 体系 |
| 不持久化有效 @ | mention 已存储，成员和角色需要在使用时检查 | 采纳；用现有结构化 mention 计算触发资格 |
| 不把 MANUAL、付款等都当永久内容拒绝 | markIntercepted 同时承载准入拒绝与业务暂停 | 采纳；安全决定与自动接待条件分开，不直接把 markIntercepted 所有原因映射 denied |
| 群审核不能改写共享原文 | insertBlockedMessage 按 id 更新 content_type=11/content，无 Agent 维度 | 采纳；保存 Agent 范围的审核结果，群共享原文不被某个 Agent 的决定覆盖 |
| 群资格校验要覆盖第一次消息 | GroupReplyRouteResolver 无旧路由会早退 absent；部分入口才调用 resolver | 采纳；提取现有资格检查，先资格后路由，不重写路由系统 |
| 不能只在提交前查当前消息发送者 | 群历史先在 forwardToAgent 拼入内容；合并队列又把拼接结果设为 rawContent | 采纳；延后历史构造；最后检查覆盖当前消息及历史来源，不能只查最后一条 fromUid |
| 多频道 Pull 分页本身已有漏读 | tools.ts 全量模式先推进各频道 MAX，再截断总 limit | 采纳；主 Agent 已独立内存复现，列为独立局部修复，不建立新游标架构 |
| 非法 @all 可以仅忽略 all、保留显式 uids | 属于可选产品语义，不是 P0 的唯一正确行为 | 不采用行为变化；已受保护路径原本拒绝非法 all，本轮统一为整条触发请求无效，不把 all 降级扩展；不额外拒绝普通、合法的显式 @ |
| 旧历史全部隔离不是唯一正确策略 | 无历史准入记录不等于确有拒绝 | 采纳其区分；撤销旧方案的单一默认结论，生产前根据只读统计选择严格或兼容迁移 |
| 无法撤回已进入原生会话的数据，也无法阻止他人重新引用 | 输入侧门禁不控制 Provider 已有记忆或文本语义来源 | 采纳；写进验收边界，不承诺追溯性清除 |

## 主 Agent 独立验证

对多频道 Pull 创建内存 SQLite：两个频道各两条消息，总数 4，limit=1。

```json
{"first":["v11"],"hasMore":true,"cursors":{"1:v1":2,"1:v2":2},"second":[],"stored":4}
```

首次只返回一条，但两频道游标都推进到 2，第二次为空。它是已复现的局部分页缺陷。其他反馈的代码位置已由主 Agent 交叉核对；本轮没有宣称它们已被修复或通过运行时验证。

## v2 二次只读审查

独立 Agent 对落地文档再次检查，发现 S1 惰性审核与 S3 游标之间的矛盾：如果所有非 @ 消息都初始化 pending，却只在被选中为上下文时才审核，最早 pending 会永久挡住后续 Pull。

主 Agent 已采纳并修正文档：

- 非 @ 消息仍在收件时记录同步黑名单等确定性拒绝；仅昂贵审核可按需进行。
- 未启动昂贵审核的非 @ 消息不假装处于 pending；缺记录默认不可注入。
- 非 @ 消息不阻塞触发游标，也不因此返回给 Provider；其上下文检查由独立有界历史查询完成。
- 只有真正待触发且正在检查的消息约束相应触发游标。

独立 Agent 的二次结论为：修正以上契约后，没有发现其他阻止该文档作为实施前计划的问题；这不等于实现或运行时安全验收通过。

## 实施后的独立复核（2026-09-07）

用户批准实施后，同一独立 Agent 对实现进行了多轮只读复核。确认并推动修复了：pending 全量 Pull 空洞、提交等待后的复查缺口、审核异常的 pending 终态、群资格等待期间权限变化、纯 Pull 未 @ 群历史、跨行/跨频道最终权限检查，以及 Console WS 后续快照泄露。

最终反馈：此前 Console 后续广播阻塞已关闭；统一广播出口逐连接隐藏实例凭据客户端的 recentEvents/recentAudit。E2EE 合并批次按每条本地消息 ID 检查全部来源，回调传递至 Provider 提交点，未见本次放宽 session/route scope。

最终源码审查结论为“暂无尚未关闭的明确阻塞项，未发现需要扩充架构的理由”。这是针对本轮实现的源码复核，不替代测试或真实 Provider 验收。实际测试与保留边界见 [实施验收记录](provider-visitor-implementation.md)。
